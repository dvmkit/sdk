# Protocol notes

## Capability schemas and signed envelopes

When descriptor-level auth is configured, `configureDVM` rejects Zod object input schemas that omit any of `pubkey`, `signature`, `timestamp` and `nonce` unless their catchall is not `never`. Declare all four fields, use `.passthrough()`, or use `z.looseObject()` to preserve them. Strict object schemas must declare all four. The protocol-owned `auth_statement` is handled separately and need not appear in the capability schema.

Unions, pipes, transforms and intersections are checked at request time. If a signed `POST /v1/quote` or `POST /v1/job` parses successfully but its schema removes supplied envelope fields, the server returns HTTP 500 `auth_error` with `sub_reason: "schema_invalid"`, names the capability and dropped fields, and logs `capability_schema_drops_signed_envelope`. The [portable response](../protocol-fixtures/auth-schema-invalid-v1.json) directs the builder to fix the schema. Callers should report this service configuration error; re-signing the request cannot fix it. Malformed caller envelopes and wrong signatures retain their existing HTTP 401 `signature_invalid` responses. No public export or storage migration changes are required.

## Missing request signatures

An unsigned `POST /v1/job` or `POST /v1/quote` that requires authentication returns HTTP 401 `auth_error` with `sub_reason: "signature_required"`. The [portable response](../protocol-fixtures/signature-required-v1.json) includes a display explaining that signing is required and a hint with two ways to sign: run `npx @dvmkit/dvm-cli init`, then `dvm request`, or implement the domain-bound signing envelope from the [protocol guide](https://dvmkit.com/docs/protocol).

A body is unsigned only when its raw structured input contains none of `pubkey`, `signature`, `timestamp`, `nonce` or `auth_statement`. A partial or malformed envelope, or a wrong signature, retains `signature_invalid` and its existing display. Input-schema violations retain their existing precedence. This adds an auth sub-reason; clients that enumerate sub-reasons must accept the new value. It does not change which requests require signing: eligible unsigned paid submits still receive their 402 challenge, while free capabilities, quotes and unsigned calls refused before payment require signing. No storage migration is required.

## Temporary job-read failures

`GET /v1/job/:id` and `GET /v1/job/:id/messages` return HTTP 503 with `Retry-After: 1` and the [portable `job_read_unavailable` envelope](../protocol-fixtures/job-read-unavailable-v1.json) when a storage connection, startup, or capacity failure prevents a read. The body has `retryable: true`, `display`, and `hint`. Retry the same read after one second, preserving the job ID, credentials, and `after` cursor. Missing credentials remain 401; an unknown job or wrong owner remains 404 when storage can be read. Other internal errors remain 500 without a retry hint.

The failure says nothing about whether the job charged, completed, or released a hold. Do not resubmit the job or repeat a payment to recover its output. A failure before an SSE stream opens returns the same JSON 503; after the stream opens, retain the existing reconnect behavior and resume from the last received cursor. No storage migration or public export changes are required.

## Payment method discovery

An explicit `paymentMethods` list bounds `payment.methods` on `/v1/info` and `/v1/quote`, the top-level `x402` and `tempo` info blocks, and credit funding rails and terms on info, quotes, and unpaid job responses. Excluded x402 and Tempo blocks are omitted rather than emitted empty. Lightning remains an independent receive-only credit funding leg. The [portable example](../protocol-fixtures/payment-method-discovery-v1.json) describes an x402/Tempo-wired DVM restricted to Cashu.

Omitting the override preserves derived defaults, including independent x402 batch credit funding when hosted exact payment is unavailable. Availability, currency support, and stablecoin-credit opt-in still filter the allowed methods. This corrects discovery on older servers that could expose excluded rails; it adds no wire fields or storage migration.

## Card-funded credit

A DVM with card credit lists `stripe` in `credit.funding` and adds `credit.stripe: { network_id, min_micro, currency: "usd" }`. It never appears in `payment.methods`, and `/v1/job` never issues or accepts a `method="stripe"` challenge.

A signed `POST /v1/credit` with `op: "fund"` and `fund.method: "stripe"` and no credential returns `402 payment_required` with one MPP `method="stripe"`, `intent="charge"` challenge in `WWW-Authenticate`, its `amount` in cents. The agent builds a credential from that challenge and the Shared Payment Token (`spt_…`) its human approved, sets `fund.commitment` to the SHA-256 of the credential, and resends the request, freshly signed, with the credential in `Authorization`. The DVM charges the token once and books a funding lot with `rail: "stripe"` and the PaymentIntent id as its reference. No exchange rate is involved: the charge is the top-up in cents.

Refusals book nothing. `credit.stripe.min_micro` is the DVM's card minimum, the builder's setting or the $5 default raised to `credit.min` and capped at `credit.max`; it is not Stripe's own minimum charge. A top-up under it returns `400 below_rail_minimum`. A commitment that does not match the credential returns `402 funding_commitment_mismatch` before any charge. A declined card returns `402 payment_invalid` with `reason: "declined"` and Stripe's `decline_code`; a token Stripe refuses outright (already used, over its approved amount, unknown) returns `402` with `reason: "token_unusable"` and Stripe's `stripe_error_code`. Both carry a fresh challenge, and the hint asks for a new top-up approval in Link, because a shared payment token can be charged only once. A replayed credential returns `409 replay_rejected`. Error bodies and logs carry Stripe's error type and codes, never Stripe's message text, which can quote the token.

Two outcomes leave a charge that may exist. If Stripe's answer is lost, the DVM returns `503` with `reason: "indeterminate"`, `retryable: true` and no challenge. If Stripe confirms the charge but the credit cannot be recorded, it returns `503` with `reason: "booking_failed"`. In both cases, resend the same credential and `fund_id` within the challenge's five minutes: the charge is idempotent on the challenge and token, so a resend that reaches Stripe's record of a successful charge books it rather than charging again. A resend does not help when Stripe's first answer was itself an error or an unfinished payment, because Stripe replays that first answer; those charges, and any left unbooked after the five minutes, need reconciliation from the provider's records by PaymentIntent. A PaymentIntent whose amount or currency is not the top-up's is never booked (`502`, `reason: "mismatch"`).

Card credit is never paid out on another rail. A drain of card-funded credit by any method other than `stripe` returns `409 card_credit_not_drainable` with a hint naming `method: "stripe"`, and `method: "stripe"` on credit funded any other way returns `409 invalid_request`. A `stripe` drain takes no `payout`; a payout field returns `400 invalid_request`. The DVM refunds the drained amount as partial refunds of the funding PaymentIntents, oldest first, each at most what that PaymentIntent has left after earlier refunds. For each one, refund = gross − round(fee × gross ÷ charged) in cents, where gross is the share of the drained balance taken from that PaymentIntent, and fee and charged are the fee and amount on the charge's balance transaction, both in the account's settlement currency. Until Stripe has recorded that fee, the drain stays `pending`. The drain response adds `refund_ids` and a `card_refund` block with `refunded_usd`, `stripe_fee_share_usd`, `refunded_cents`, `stripe_fee_share_cents`, `sub_cent_micro` (drained value below one cent, not refundable) and the per-PaymentIntent `refunds`. The drain's `amount_micro` is the whole balance drained; the fee share is part of it. A refund Stripe has not finished, or refused, leaves the drain `pending`; polling the drain retries it without refunding twice. One card refund runs at a time: a new `stripe` drain while another is pending returns `409 drain_conflict` with `blocking_drain_id` and `retryable: true`; poll that drain until it is sent. A `stripe` drain id is at most 128 characters and may not start with `expiry-`, which is reserved for expiry refunds (`400 invalid_request`).

An expired card balance is not released to the provider: the DVM refunds it to the card the same way and the credit closes with `status: "refunded"` and `refund_drain_id`. A dispute on a funding PaymentIntent freezes the credit with `status: "disputed"` while it is open or lost; once every dispute on all of its top-ups is won, however old, the credit is `active` again; a lost dispute keeps it frozen. A top-up of an expired card credit returns `409 credit_closed` before any challenge is issued. A closed or frozen credit refuses draws, top-ups and drains with `409 credit_closed`, `retryable: false`. The [funding example](../protocol-fixtures/credit-fund-stripe-v1.json) and [refund example](../protocol-fixtures/credit-drain-stripe-v1.json) are consumed by the SDK tests.

## Payment message history

Requester `payment` messages in `GET /v1/job/:id/messages` (JSON or SSE) and saved job history are published only after the server accepts the payment through its verification and accounting flow. Pending and rejected attempts are omitted, including attempts that fail signature verification. A rejected attempt does not satisfy the outstanding payment request; a later valid payment can still be accepted. Explicit development-mode acceptance follows the same history rule even when verification is bypassed.

An unsupported payment method is rejected with HTTP 402 `payment_invalid`, rather than acknowledged without verification. While a payment is pending, message reads and streams hold later output behind it so an `after` cursor cannot skip a payment that is accepted later. Every host, including the active worker, uses the shared store's message sequences and delivery cutoff. Rejection releases that output without publishing the rejected attempt; completion, failure and cancellation release final output immediately. Payment sequence bindings remain unchanged.

Terminal snapshots retain every verified message, including accepted payments beyond an unresolved earlier attempt. `StreamableJobStore.getMessages` accepts an optional third argument `{ includeHeld: true }` for this complete verified read; custom stores that implement the delivery cutoff must honor this option when building terminal snapshots. Incremental reads retain the cutoff by default, and terminal history remains readable after incremental rows are cleaned up.

Message sequences can have gaps where attempts were rejected. A history entry records acceptance, not final job settlement, and does not by itself prove that all funding was applied to the job: retain any credit explanation and signed funding or settlement evidence returned by the server. An absent entry alone does not authorize another spend after an unknown outcome; use the payment method's recovery evidence. Older servers and snapshots created before this fix may contain rejected payment attempts without a rejection marker; those entries cannot establish acceptance under this contract. No wire fields or storage migrations are added, and old snapshots are not rewritten.

## Accepted upfront payments

Successful submit (`POST /v1/job`), request-resume and request-result responses, and authenticated job reads, may carry `upfront_payment`. It records the original accepted payment before the handler runs. `amount_msats` is an integer millisatoshi value from the accepted payment or committed credit allocation, not a new quote or conversion at the current exchange rate. When a draw exists, `amount_micro` and `currency` preserve its exact credit denomination in integer millionths; `native_amount` and `native_asset`, when present, describe its allocated rail-native atomic units. A funding deposit may exceed all of these job amounts.

`credit_id` and `draw_id` together identify credit consumption, including an implicit credit opened by a per-call payment. `rail` identifies the rail that funded that credit, not a fresh payment on recovery. Without a credit draw, the block reports the verified per-call rail payment. No payment credentials are included. The portable examples are in [upfront-payment-v1.json](../protocol-fixtures/upfront-payment-v1.json).

For a credit-backed job the block describes the **hold at acceptance**. Completion settles the draw; any other ending settles its finished pieces and releases the rest (see [charging by the piece](#charging-by-the-piece)). Later top-ups, draw growth, settlement repricing, refunds and exchange-rate changes do not rewrite the acceptance snapshot. It is neither a current balance nor a signed terminal receipt. Use the terminal receipt for final settlement evidence; do not count the funding deposit and its job draw as two payments for the same service.

An explicit `amount_msats: 0` is known zero in that unit; a positive `amount_micro` can still describe a credit hold whose allocated millisatoshi value rounded to zero. An absent block means unknown, including jobs accepted by older servers and development submissions that bypass verification. Callers must not substitute zero for absence. Caller transport result types expose this block as optional `upfrontPayment`, retaining snake_case inside the block.

The additive nullable `jobs.upfront_payment` column is written only when the job is first inserted. Existing records are not backfilled from cumulative totals or current draws. Custom job stores must preserve this field through reads and snapshot saves without replacing the first stored value, including its absence. Deploy the upgraded writer to obtain the field on new jobs; older writers and older job records can still omit it.

The supported public type is available without a deep import:

```ts
import type { JobRecord, UpfrontPayment } from "@dvmkit/sdk";

function originalHold(job: JobRecord): UpfrontPayment | undefined {
  return job.upfrontPayment;
}
```

## Cashu lock requirements

A Cashu payment on `X-Cashu`, a mid-job `payment` message or `POST /v1/credit` must be spendable only by the DVM until the batch melt, and in a form the DVM can sign and the mint can redeem. Each proof must be NUT-11 P2PK-locked with `data` set to one of `cashu.lock_pubkeys` from `/v1/info` (the first entry is current; later ones are retired keys still in grace), written as a 33-byte compressed hex key (66 hex characters, `02` or `03` prefix, no whitespace); x-only keys are refused. The only tags allowed are `locktime`, `refund`, `pubkeys`, `n_sigs`, `sigflag`, `n_sigs_refund` and `refund_delay`. Each may appear at most once and must carry at least one value; `locktime`, `n_sigs`, `sigflag`, `n_sigs_refund` and `refund_delay` carry exactly one. Any other tag is refused. A `refund_delay` tag is what a wallet copies from a payment request that carries one ([NUT-24 payment requests](#nut-24-payment-requests)); it sets no spending condition, mints ignore it, and the DVM judges the proof as if it were absent. A `pubkeys` tag may name only other `cashu.lock_pubkeys` entries, with no key repeated across `data` and `pubkeys`. `n_sigs`, if present, must be `1`, and `sigflag`, if present, must be `SIG_INPUTS`. `refund` keys must be distinct compressed keys, and `n_sigs_refund` must be a positive integer no larger than the number of refund keys. A `locktime` tag must be a plain decimal unix-seconds value, with or without `refund`, and at least `cashu.min_locktime` minus 24 hours after the moment the DVM receives the payment. An unsigned `POST /v1/job` payment sent without `X-Cashu-Request-Id` ([NUT-24 payment requests](#nut-24-payment-requests)) is held instead to the unsigned floor, with no 24-hour margin: `cashu.unsigned_min_locktime` seconds after receipt when `/v1/info` advertises it, otherwise `cashu.min_locktime` minus 24 hours ([Refund-locktime floors](#refund-locktime-floors)). A proof with no `locktime` is accepted. A secret longer than 1024 characters, the default limit a Nutshell mint redeems, is refused, and so is a secret the cashu-ts signer cannot parse. A `data` key that is not a DVM key in that form returns HTTP 402 `wrong_lock_pubkey`; any other refused lock returns HTTP 402 `lock_not_exclusive`. Both answer 400 instead for a `POST /v1/job` payment sent without `X-Cashu-Request-Id` ([NUT-24 payment requests](#nut-24-payment-requests)). Both are decided before the mint is contacted or anything is recorded. The refusal's `hint` names the floor that applied: `cashu.min_locktime` minus 24 hours, or `cashu.unsigned_min_locktime`. A retry of a payment the DVM already banked still returns `409 replay_rejected` after its locktime has dropped below whichever floor applies to the retry. An `X-Cashu-Request-Id` (or a mid-job payment's `cashu_request_id`) belongs, per DVM, to the first proof set banked under it. A payment whose proofs are all new to the DVM but whose request id is already used, upfront on `/v1/job`, in a mid-job `payment` message or on `POST /v1/credit`, is refused with HTTP 409 `request_id_reused` before anything is recorded, so nothing is charged and the same proofs can be sent again under a new request id. A `POST /v1/job` retry with already banked proofs gets the original job's response back, `job_token` included, only when every presented proof was accepted under the retry's `X-Cashu-Request-Id`, the body matches the paid request and, on a signed DVM, the same key signs it. Any other presentation of banked proofs, including proofs accepted under different request ids, gets `409 replay_rejected` with no job and changes nothing.

## NUT-24 payment requests

A `POST /v1/job` that needs no signature (any request to a DVM without auth, or an unsigned request to a DVM built with `secp256k1Auth({ allowUnsignedPaid: true })`) can be paid the [NUT-24](https://github.com/cashubtc/nuts/blob/main/24.md) way. When such a request needs a payment and carries none, a DVM that takes P2PK-locked Cashu answers its HTTP 402 `payment_required` with an `X-Cashu` header holding a NUT-18 `creqA` payment request: `a` is `required_msats / 1000` rounded up, `u` is `"sat"`, `m` is the mint list `/v1/info` advertises as `cashu.mints`, and `nut10` is `{ kind: "P2PK", data: cashu.lock_pubkeys[0], tags: [] }`. It names no id, description, single-use flag, transport or `locktime`, so payment is in-band. A builder who sets `cashu.advertiseRefundDelay: true` in `configureDVM` adds one tag, `["refund_delay", "<seconds>"]`, telling the wallet it may lock its proofs with a `locktime` at least that far ahead and a `refund` key of its own, so a payment the DVM never redeems goes back to the payer. `<seconds>` is the floor a retry carrying the same headers is held to ([Refund-locktime floors](#refund-locktime-floors)) plus 600: the unsigned floor for a request without `X-Cashu-Request-Id`, the signed floor less its 24-hour margin for one that sends it. The extra 600 seconds cover the time between the wallet reading the 402 and the DVM receiving its payment, the same 10 minutes the price hold below allows, so a lock at the wallet's clock plus `<seconds>` clears the floor at receipt. The option is off by default; leave it off until the mints and wallets your callers use support the tag. As NUT-18 specifies, `a` is what the DVM must receive net of the mint's NUT-02 input fee: the payment counts as its proofs' face value minus the fee to spend them, so the wallet adds that fee on top of `a`. At a mint with no input fee the two are equal. No other response carries `X-Cashu`: not a refused payment, not a 409, not `POST /v1/credit`, and not a signed request's 402, which still needs `X-Cashu-Request-Id` to pay. A development host's CORS policy exposes the header to browser wallets.

The wallet retries with only `X-Cashu: cashuB…`. The token must meet the [Cashu lock requirements](#cashu-lock-requirements). With no `X-Cashu-Request-Id`, the payment is bound to `nut24-` followed by the hex SHA-256 of its JSON-encoded, sorted proof secrets, and that id takes the place of a request id everywhere: in the accumulator's replay binding, as the job's payment reference and as the implicit credit's funding id. Retrying the same token with the same body returns the original job, `job_token` included, and records nothing new; the same token with another body gets `409 replay_rejected` and no job. A header-less payment refused for a reason the payer can fix answers HTTP 400 with the usual JSON body: `invalid_token` (a mint outside `m`, a unit other than sat, missing DLEQ evidence or an unreadable token), `not_p2pk_locked`, `wrong_lock_pubkey`, `lock_not_exclusive` and `payment_insufficient`. Other refusals keep their status, including `proof_not_unspent` (402), `proof_pending` and `mint_unreachable` (402), `mint_health_pending` and `cashu_mint_sick` (503), and `replay_rejected` (409). A short header-less payment is kept, exactly as a short payment with a request id is, and answers 400. Requests that send `X-Cashu-Request-Id` answer as before, except that an id starting with `nut24-` is reserved for derived ids: `POST /v1/job` refuses it with HTTP 400 `reserved_request_id` before pricing or recording anything, with or without a token, and the receive path refuses it the same way on a mid-job payment's `cashu_request_id` and on `POST /v1/credit`. Without that refusal a caller could claim another payer's derived id first and have the honest payment turned away.

After accepting an unsigned payment with only `X-Cashu`, the submit waits up to 10 seconds for the job, including a retry that recovers a running job. Completion returns HTTP 200 with `job_id`, `job_token`, `status: "completed"`, the summary or artifact metadata, and the existing terminal and content fields. `DVM-Job-Identity-V1` identifies the job on both 200 and 202 responses. A job still running at the deadline returns the usual HTTP 202 response; use its job token to poll `/v1/job/:id/messages`. An `awaiting-input` job returns its usual 202 response immediately, and failed or cancelled jobs also return through the existing submit response mapping (202). Disconnecting stops the wait and leaves the job running; retry the same token and body to recover it without another charge.

For a completed artifact result on this path, the 200 body also includes `messages`: the same durable array, entries, field names, and artifact encodings returned by `GET /v1/job/:id/messages`. A client can parse the artifact directly from the paid retry, and an identical paid retry returns the same messages without another charge. This array is included only when its complete JSON serialization is at most 1,048,576 UTF-8 bytes. Larger results omit `messages` and retain `payload_in: "messages"` so the client can fetch them separately. The fixed cap limits per-request server memory and the body buffered by a small client or agent context. Content holds and retention apply as on the messages endpoint; unavailable content is never inlined. Signed submits, explicit-request-id Cashu, job reads, and other payment methods keep their existing response fields.

Set `cashu.unsignedResultWaitSeconds` in `configureDVM` to an integer from 0 to 20; 0 disables waiting. The 20-second ceiling leaves time for a cold machine wake under an HTTP proxy's common roughly 30-second request deadline. Signed calls, prepaid credit, x402, Tempo, and Cashu calls carrying `X-Cashu-Request-Id` keep their existing response timing. The wire contract is in `protocol-fixtures/nut24-inline-result-v1.json`.

A USD price is converted to sats from a rate the DVM refreshes every few minutes, so the `a` a wallet was shown can fall short a moment later. A header-less payment that covers the price at the rates the current ones replaced, but not at the current ones, is accepted and valued at the earlier rates while those rates last priced something (a quote or a 402) less than 10 minutes ago: long enough for a wallet to read the 402, prepare proofs at its mint and resend, short enough that an old quote does not stay payable for the life of the next one, and a DVM that sat idle through a rate change honours no hold when it wakes. The hold is taken from the rates this request was priced at, so a refresh landing while the payment is verified does not move it. One that covers neither is short. A payment sent with `X-Cashu-Request-Id` gets no hold.

## Caller response deadlines

Every newly emitted `prompt` and `payment-request` carries `content.expires_at_ms`, an integer Unix millisecond deadline equal to emission time plus the DVM's `idleTimeout` in milliseconds. The window starts when the handler asks, and ends when the matching response or verified payment satisfies that ask. Text and unrelated responses do not extend it. This includes event-driven requests emitted through `ctx.sendMessage`, which keep callback dispatch semantics. Processing without an outstanding ask has no idle timer; worker liveness remains governed by `processingWatchdog`.

`configureDVM` accepts `idleTimeout` as a whole number of seconds from 1 through 604800 (seven days), defaulting to 3600. Replayed requests retain their original deadline and payment challenge. With concurrent prompts, the earliest outstanding deadline governs cancellation; answering one does not extend the others. Expiry is attributed to the caller.

The job expires 30 seconds after that deadline, not at it, on every expiry path: the idle timer, the stale sweep and a store's cancellation check. `expires_at_ms` itself is unchanged on the wire. A payment that arrives within those 30 seconds still pays the ask; one that arrives later lands as balance (see [Payments that arrive as a job ends](#payments-that-arrive-as-a-job-ends)).

If a worker dies after input verifies but before claiming it, recovery can fail the abandoned job as a provider failure and release its pending draw. This waits for both the stale-wait threshold and processing watchdog grace period; verified input remains in the terminal history.

The wire field is optional for compatibility with older servers; callers may ignore it. Legacy persisted waits without a stamp retain their timeout fallback, and older server versions cannot enforce the new semantics during a mixed-version rollout. No storage migration is required. Portable examples are in `protocol-fixtures/caller-deadline-v1.json`.

## Durable steps

`ctx.step(id, fn)` caches a completed operation's result and cost declarations for handler replay. With Postgres, or a custom `JobStore` implementing optional `saveStep`, the SDK waits for the step record's durable write before resolving the step. Each write updates only the step cache; it does not rewrite the message log. Writes are attempted at most three times, with 50 ms and 100 ms backoffs. If all attempts fail, the SDK emits `step_persist_failed` and returns the result anyway: the external action may already have happened. That result remains available to later yield and terminal snapshots, but is not yet guaranteed durable. Custom stores without `saveStep` retain yield/terminal snapshot persistence. In-memory stores cannot survive process death.

Steps have **at-least-once** execution semantics. A body can run more than once if the process dies mid-body, after an external side effect but before the result is stored, or after exhausted persistence retries. For irreversible actions, pass `${ctx.jobId}:${stepId}` as an idempotency key to an external API that honours it, or check that system for a prior result before acting:

```ts
const stepId = "reserve-instrument";
const reservation = await ctx.step(stepId, () =>
  instrument.reserve({
    idempotencyKey: `${ctx.jobId}:${stepId}`,
  })
);
```

The job id and step id stay stable across replay. A cached step returns its stored value and replays its cost declarations without calling the body. Step ids must be unique within a job. This does not add recovery of abandoned processing jobs; their existing watchdog behavior is unchanged.

Compatibility: `JobStore.saveStep` is additive and optional, and uses the existing `step_cache` column without a migration. Implementations preserve the first stored record for each step id, keep those records through later snapshots, and reject writes to missing, terminal or redacted jobs.

## Refund-only JIT park

`POST /admin/credit/park-drain` accepts a just-in-time mint refund (`consumed_row_ids: []`, `keep_proofs: []`, valid `mint_evidence`) whether or not Cashu accumulator mode is on, so a Lightning-funded service can return a deposit through its refund mint without enabling incoming Cashu. It keeps the authenticated builder-lock check, the drain/credit binding, mint and face-value agreement with the token, the drain's P2PK `refund_pubkey` lock, the mint UNSPENT check, and the single ledger compare-and-set: the same token replays idempotently, even after pickup, and a different token conflicts. It never reads or writes `wallet_accumulator`. Requests without valid evidence, or with accumulator rows or change, still return HTTP 503 `accumulator_not_wired` when accumulator mode is off.

`/v1/info` advertises `credit.jit_refund_park: true` when the service mounts this route (database, DVM ID and persisted lock key present). Missing or any other value means unsupported; do not infer support from missing accumulator metadata, a 404 batch route, SDK version or `sdk_sha`. Check it before quoting or paying a fresh JIT refund purchase. The additive field is `CreditTerms.jit_refund_park`; examples are in [jit-refund-park-v1.json](../protocol-fixtures/jit-refund-park-v1.json).

## Balance-backed mid-job payments

A server advertising `credit.balance_payment: true` accepts a signed balance authorization on the existing `POST /v1/job/:id/messages` endpoint with the existing job token. This capability requires the SDK's Postgres job store and credit ledger on the same database, descriptor authentication, and an audience verified from the builder attestation. The normal Postgres host wires these together. In-memory development stores and custom job stores withhold the capability; ordinary messages and rail payments keep their existing contract. The memory ledger enforces expiry and its configured x402 refund gate for `growDraw({ spendExistingBalance: true })`. Fresh growth on Tempo-bound memory credit returns `tempo_channel_closing` because this store cannot verify the durable channel lifecycle; ordinary accepted rail growth retains its existing behavior.

A `payment-request` may include `content.credit: { amount_micro, currency }`. These are the exact uncovered ask in integer millionths of the credit denomination, pinned when the ask is persisted. Use the enclosing message's `seq` as `request_seq`. If exact denomination is unavailable, this field is absent and callers must use an offered rail.

Send `{ type: "payment", content: { credit: authorization } }`. The authorization contains `credit_id`, `draw_id`, `payment_id`, `request_seq`, `amount_micro`, `currency`, and the existing `pubkey`, `signature`, `timestamp`, `nonce`, `auth_statement` envelope. Sign it with the existing caller signing API. Its audience is the verified service identity, method is `POST`, path is the concrete messages path including the job ID, and capability is `null`. No rail credential or other payment content may accompany `credit`. Currency names are lowercase ISO 4217 codes. A zero-upfront job can bind its first draw; a job already holding a draw must name that same credit and draw.

Success is HTTP 201 `{ seq }`, naming the durable verified inbound message. `payment_id` is a separate host-wide identity, independent of funding, draw and drain IDs. Reusing an accepted identity with identical monetary fields, owner, job and signing domain returns the original status and body, even after completion, restart or expiration of the signature's freshness window. A newly signed envelope for the same accepted intent also recovers that result. Altered reuse returns HTTP 409 `credit_payment_conflict`. Retain the exact authorization and identity through ambiguous delivery; never create another spend to recover a lost response.

Fresh authorization still checks signature freshness, job ownership, credit ownership, draw binding, and the persisted outstanding ask before holding money. An authorization for the current ask made 30 seconds or more past its `expires_at_ms` is refused with HTTP 409 `ask_expired` and moves no money. Competing IDs for one ask serialize; once one pays it, another receives HTTP 409 `credit_payment_ask_mismatch`. That same error covers a stale sequence, changed amount or changed ask currency. HTTP 409 `credit_payment_currency_mismatch` means the named credit has a different denomination; `credit_payment_owner_mismatch` means it does not belong to this caller and job. These refusals move no money: refresh the job or refuse locally. They do not authorize an invented rail fallback. Existing authentication errors and job-token refusals remain unchanged. Expired, closed or settlement-blocked credit returns its existing ledger error with HTTP 409 and no debit.

HTTP 402 `{ error: "insufficient_credit", remaining_micro, shortfall_micro }` moves no money and keeps the ask available for an ordinary rail payment. It does not reserve the payment ID; the same intent may be retried after funding. HTTP 400 `invalid_message` refuses mixed credit and rail content. Unsupported storage returns HTTP 409 `balance_payment_unavailable`.

Fresh balance growth also uses the existing hosted obligation fence, so a closed host cannot acquire a new hold. The credit/channel locks, draw placement or growth, job accounting, verified inbound and original response commit together. A balance-paid ask buys the next piece of work like any other payment, and the draw settles by the piece ([Charging by the piece](#charging-by-the-piece)); what it releases is caller-owned spendable credit, available to the existing drain lifecycle. Balance spending creates no funding deposit and retains one draw and one revenue basis per job.

## Payments that arrive as a job ends

Every rail payment sent on `POST /v1/job/:id/messages` is recorded when it arrives, before its rail is verified, under the job's row lock. That record fixes what the payment is for. It pays the open ask when the job is still running, an ask is outstanding, and the payment arrived less than 30 seconds past the ask's `expires_at_ms`. Otherwise it lands on credit as balance and buys nothing: when the job has ended (completed, failed or cancelled), the ask expired, or no ask is open. Arrival time decides, not the time verification finishes.

A payment meant for the ask also lands as balance when the job's credit cannot take it: the credit holds another rail (sats and USDC do not mix) or is bound to a reusable channel, or the job's credit or draw is unavailable. It then funds a fresh `imp:<rail>:<payment id>` credit owned by the same caller, and the ask stays open. To make this rare, an ask on a job bound to a credit funded on Cashu, x402 or Tempo offers that rail alone; when that rail is not one the ask would otherwise offer, it keeps every option rather than offer none. A Cashu wallet may still fall back to `/v1/info` when an ask carries no `mints`, so a payer should pay on a rail the ask names.

A payment that lands as balance answers HTTP 201 `{ seq, credit }`. `credit` names the credit that holds it, with `credited_micro` and `credit_currency`, and the handler is not resumed. Because it paid no ask, it does not appear in the job's message history, and a replayed handler never counts it as payment; the `credit` block and the credit's funding are its record. Its `hint` says why; for a rail mismatch it names the rail the job's credit holds. A signed caller's payment lands on the job's own credit when that credit can take it, otherwise on a fresh credit owned by the same key; either way the caller can spend it with a balance payment or reclaim it with op `drain` at `POST /v1/credit`. An unsigned payment is final: it lands on its own `imp:<rail>:<payment id>` credit, which no caller key can drain. A rail payment on an ended job is therefore accepted on that basis instead of refused with HTTP 409 `job_not_active`; a message carrying no payment still gets `job_not_active`.

While a recorded payment is being verified, the job cannot end. A cancel, an ask expiry, the stale sweep and the handler's own terminal write wait until the payment's outcome is recorded, so a payment that races a cancel either pays the ask before the cancel commits or, arriving after it, lands as balance. Waits poll with doubling intervals from 100 ms to 2 seconds. A cancel, or a message that would fail a job whose capability is gone, holds its HTTP request for at most 5 seconds and then answers HTTP 409 `payment_in_progress` with `Retry-After: 2`, changing nothing; retry it. The payment's own hold is bounded too: an arrival holds the job for at most two minutes, which covers the 60-second settlement window an x402 authorization advertises. If the verifying process dies, the job can end once that lease passes. A verification that still completes later pays nothing to the ended job: the job's draw has resolved, or the store refuses to credit or bind an ended job and the draw the payment opened is released at once, so the money lands as balance.

No payment is accepted without a ledger row. A payment is valued in the credit's currency from the ask's pinned envelope, else a live or cached rate, else what the ask itself quoted (its x402 `required_usdc_micro`, else its `fiat_amount`). A mid-job payment is refused before its rail is touched, so the same artifact can be sent again, in two cases only: the DVM has no credit ledger (HTTP 402 `payment_invalid`), or there is no rate and the payment has no ask quote to value it (HTTP 503 `fx_rate_unavailable`, retryable). A Cashu token refused this way is refused before its proofs are stored and stays unspent. Each refusal ends the payment's hold on the job. An x402 settlement that reports no transaction hash is recorded under its EIP-3009 authorization (`eip3009:<from>:<nonce>`), which is single-use on chain.

The balance authorization is the only mid-job payment checked before money moves (a pre-flight): there is no separate payment-request refresh, job quote or challenge endpoint, since x402 and Tempo challenges ride inside the ask. It alone answers HTTP 409 `ask_expired` after the deadline; rail payments land as balance instead.

An ask on a job bound to a credit offers only that credit's rail when it can. A cancel held by a payment in flight can answer 409 `payment_in_progress`. A mid-job payment on a host without a credit ledger is refused. `ask_expired` is a new balance-payment refusal. The internal `processIncomingPayment` now runs the ledger leg and requires `creditLedger`.

## Charging by the piece

Each payment buys the next piece of work. The upfront payment buys the first piece; each paid `payment-request` buys the piece after it. A piece is finished when the DVM sends its next `payment-request` or completes the job. However a job ends, the caller is charged for its finished pieces. When the job fails, its handler throws, the caller declines or an ask expires, the piece in progress is released to the caller's credit. A caller's cancel (`DELETE /v1/job/:id` or a `cancel` message) is the one exception: it stops the work at once, exactly as before, and charges the piece in progress with the finished ones. A cancel never spends new money; it only keeps payments the caller already made. A job with no asks is one piece: charged if it completes or is cancelled, released if it fails. An unsigned x402 job stays one piece settled only on completion, so a cancel charges it nothing; an unsigned Cashu payment is final either way.

For example, a job takes $0.10 upfront, then asks $0.20, then $0.50:

| Ending | Charged | Released |
| --- | --- | --- |
| Completes | $0.80 | $0 |
| The provider fails during the $0.20 piece | $0.10 | $0.20 |
| The caller declines the $0.50 ask | $0.30 | $0 (never paid) |
| The caller cancels during the $0.20 piece | $0.30 | $0 |
| The $0.20 piece finishes at a lowered $0.05, then the job completes | $0.65 | $0.15 |

Every ask is new money: the upfront payment is never spent on an ask, however large it was. A job has one open `payment-request` at a time; a payment that arrives with no ask open lands as balance and buys no piece ([Payments that arrive as a job ends](#payments-that-arrive-as-a-job-ends)). Amounts are integer micro-units of the job credit's currency, and the figure the draw settles is computed once, in the transaction that makes the job terminal, and frozen on the job row; every later resolution of the draw settles exactly that figure.

A `payment-request` carries `charged_if_declined_micro`: the pieces finished so far at their charge, a lowered `finishedChargeMicro` where the DVM gave one, which is exactly what declining that ask settles. A caller ends a job at its open ask or prompt with `{ type: "decline", content: { reason? } }` on `POST /v1/job/:id/messages`. The job ends `cancelled`, ended by the caller, with the piece in progress released; at an open ask nothing is running, since the ask finished it. The answer is HTTP 201 `{ seq }`. With no ask or prompt open the decline is refused with HTTP 409 `no_open_ask` and changes nothing; a payment still being verified holds it as it holds a cancel (HTTP 409 `payment_in_progress`).

A terminal job's signed receipt keeps `v: 1` and, when the job held a credit draw, gains an optional `settlement` block: `{ held, charged, released, pieces: [{ amount, charged, paid_seq, state }] }`. `paid_seq` is the sequence of the payment message that bought the piece, `0` for the upfront payment; `state` is `finished`, `stopped` (a cancel charged it) or `released`. `credit.amount` is now the amount charged, `0` on a draw released whole; receipts issued before this change named the hold there on a released draw. `paid` keeps meaning what the caller's payments credited. `pieces` is empty on a job accepted before piece charging, which settles as one piece. The terminal report to the platform gains `chargedMicro`, its `currency` (`null` without a draw) and `stoppedPiece`, true when a cancel stopped a running piece and charged it. Reports also carry `heldMicro`, the original hold including all paid mid-job pieces, and `finishedPieceCount`, the number of finished paid pieces excluding a stopped piece. The hold is `0` without a resolved draw; an unpaid unsigned x402 job reports a zero hold and count, and a successfully settled one reports one finished piece. Historical jobs without a piece list omit the count. Both additions are optional: consumers must accept older reports without them and ignore unrecognized fields. A caller reconciling its credit (`applyReceiptCredit`) checks a receipt whose `settlement.charged` is positive on every ending, comparing the charge and the reported balance with its own payments: its prior balance plus the verified funding of the draw.

Builders: deliver a piece's output, its artifacts or partial results, before asking for the next payment, because the ask finishes the piece and a caller who declines it has already paid for that output. Ask a prompt question before the payment request whose work depends on the answer, not after it: a decline at a prompt releases the piece in progress, so a question asked after the payment leaves that paid piece at the caller's discretion. For metered work, ask at the cap and report what the piece used on the call that finishes it, `ctx.requestPayment(..., { finishedChargeMicro })` or `ctx.complete(summary, { finishedChargeMicro })`; the charge must not exceed that piece's price, and the difference goes back to the caller when the job ends. A second `ctx.requestPayment` while one is open rejects with code `ask_already_open`, and `ctx.complete` with an ask open withdraws it, so a payment arriving afterwards lands as balance.

A second open ask rejects with `ask_already_open` instead of replacing the first. `credit.amount` on a receipt is the charged amount. ## Mid-job draw funding evidence

A rail payment accepted on `POST /v1/job/:id/messages` while a job runs funds the job's credit and grows its pending draw in one ledger step that allocates no sequence. The terminal receipt's `credit.balance_after` therefore includes that money while a caller projection anchored before the draw does not. The server now records every such funding as a `credit_fundings` row keyed on the rail payment id, with the job, draw and accepted payment message sequence, inside the same transaction as the processed-payment marker, the fund and the growth, and signs a `credit_draw_funding` receipt from that row with the per-DVM receipt key.

The artifact is `{ v: 1, kind: "credit_draw_funding", credit_id, job_id, draw_id, fund_id, payment_seq?, currency, funded_micro, balance_after_micro, ledger_seq, issued_at, caller_pubkey, dvm_id, dvm, receipt_pubkey, signature }`. `fund_id` is the rail payment id. `funded_micro` is the provider's credited amount after its own denomination and fee rules, never the caller's request figure. `ledger_seq` is the draw's own sequence, the value the terminal `credit.ledger_seq` names; `balance_after_micro` is the spendable balance immediately after the funding and any growth committed. Signing and verification use the existing receipt canonicalisation and attestation chain. Opening and `/v1/credit` funding receipts keep `kind: "credit_funding"` and their meaning; a job-bound funding row is never signed as one, so a fund replay that names a mid-job payment id carries no `funding_receipt` and the draw funding artifact stays issuable. `payment_seq` is the accepted inbound payment sequence, fixed in the signed funding evidence; it is omitted when the job store does not number inbound messages.

The successful payment response is HTTP 201 `{ seq, credit?, draw_funding_receipt? }`. The same artifact rides the `503 job_snapshot_unavailable` and `500 payment_unapplied` bodies, because the funding committed before those failures. A replayed x402, Tempo or Cashu payment returns its existing `409 replay_rejected` with `draw_funding_receipt` when the DVM can name the payment it collided on; a replayed exact x402 settlement recovers as before and carries it on the 201. Authenticated `GET /v1/job/:id` returns `draw_funding_receipts`, oldest first, reissued from the committed rows when an acknowledgement was lost or the process restarted; the key is omitted when there are none. Balance-paid asks fund nothing and produce no artifact. Free-then-paid jobs open an implicit credit and produce none either. Payments that grew nothing still produce one, because the balance moved.

In the successful standard message response, acknowledgement `seq` is the latest message position observed after dispatch. Provider messages emitted during dispatch can advance this cursor, so it can equal or exceed the accepted payment's sequence. It does not replace signed `payment_seq` or the credit draw's `ledger_seq`. Separately, `503 job_snapshot_unavailable.seq` identifies the recorded inbound payment, not a post-dispatch cursor.

For example, a payment accepted at message sequence 8 retains signed `payment_seq: 8`. If the provider emits message 9 during dispatch, the acknowledgement returns `seq: 9`. This 8/9 pair is valid when all existing funding verification requirements pass: cursor equality is not required, and neither equality nor a cursor value alone establishes validity. A larger acknowledgement cursor relaxes none of the signature verification or caller, service, credit, job, draw, payment, currency, and ledger binding checks.

Caller reconciliation: admit each artifact through `recordDrawFunding`, or pass it to `applyReceiptCredit` as `drawFundings` so admission and comparison share one lock. Admission verifies the signature, the caller, the credit, the currency and the provider chain; an attested record requires the artifact to chain to its own builder. The completed-draw comparison becomes `remaining + sum(funded_micro of facts bound to the receipt's draw_id and ledger_seq) − amount`. A fact applies once, only to that receipt, and is refused as already reflected when the projection is anchored at or beyond its sequence. Absent, invalid, wrong-bound or duplicate evidence leaves the existing comparison and warning in force.

## Completed credit draw refunds

`POST /admin/credit/refund-draw` uses the existing signed builder-admin authentication. Its JSON body names either `jobId` or `creditId` plus `drawId`, a required caller-chosen `refundId`, an optional positive safe-integer `amountMicro`, and an optional `reason` of at most 280 characters. Omitting the amount means the draw's remaining unrefunded charge. The amount is in millionths of the original credit currency. A refund restores spendable credit; the caller can spend it again or reclaim it through the existing drain.

The server entry point also exposes `CreditDrawRefundArgs` and `CreditDrawRefundResult`. Custom `CreditLedgerLike` stores must implement `refundDraw`; production implementations must commit accounting and the outbox atomically. `MemoryCreditLedger` provides development accounting only and is refused by the admin route.

The success response contains `status: "refunded"`, `refund_id`, `credit_id`, `draw_id`, `job_id`, `amount_micro`, `currency`, `ledger_seq`, `refunded_at`, `balance_after_micro`, and `replayed`. Repeating the same ID and arguments returns the persisted original amount, currency, sequence, timestamp, and balance after that refund. That balance is historical, rather than the caller's current balance. An omitted amount stays the same remainder intent on retry; changing it to an explicit amount is a conflict even when the numbers match.

Eligibility refusals carry relayable `hint` text: `draw_not_found` (404), `draw_not_completed`, `refund_exceeds_draw`, `credit_not_open`, `credit_refund_channel_unsupported`, `credit_refund_state_unavailable`, and `credit_refund_basis_unavailable` (422). A changed-argument reuse returns `refund_conflict` (409). Missing persistent accounting or platform reporting returns `credit_refund_unavailable` (503) before any money changes. Existing malformed-request and authentication conventions remain. Tempo and reusable x402 channel credits cannot back a refund of already settled spending; unused channel collateral returns through its channel lifecycle.

The credit balance, rail remainder, refund history, funding lots, and report outbox row commit together. A failed enqueue rolls everything back. The new outbox kind `refund` sends `POST /_internal/credit-draw-refund` with `dvmId`, `creditId`, `drawId`, `jobId`, `refundId`, `amountMicro`, `creditCurrency`, `ledgerSeq`, `refundedAt`, and optional `reason`, authenticated with the existing DVM bearer token. The platform deduplicates by refund identity. A missing original revenue event returns 409 and remains queued for retry; cumulative excess returns 422 and becomes stale for operator inspection. Existing transport backoff and 24-hour abandonment remain. The [portable fixture](../protocol-fixtures/credit-draw-refund.json) pins the request, success, report, and historical-evidence refusal shapes.

Bitcoin refunds restore the original settled sats, never a current exchange rate or the draw's pooled forecast. For original micro amount `M`, proven settled sats `S`, and cumulative refunded micro `R`, restored sats total `floor(S * R / M)`. Each refund restores only the increase, so a full refund returns exactly `S` regardless of partial-refund sizes. Integer rounding may produce a valid zero-sat lot. Such a lot stays explicitly known-zero through later settlement, liability reporting, and reclaim; it never triggers live-rate pricing.

Schema initialization adds nullable `credits.last_funding_ledger_seq`, `credit_draw_refunds`, nullable `credit_draws.settled_sats` and `credit_draws.refund_dvm_id`, and `credit_funding_lots.sats_basis_known` defaulting to false. Historical positive lots remain priced; historical zero-sat lots remain unknown. New fully priced settlements record their authoritative sats even when equal to their forecast. Only an authoritative actual-settlement `settled_sats` value, including zero, authorizes Bitcoin restoration. An old `allocated_msats` repricing marker alone does not independently establish the original payment value. Retained funding receipts establish deposits rather than a completed draw's consumed lot allocation, so this route has no automatic proof path for older completed Bitcoin rows missing `settled_sats`. Those rows, retained forecasts, missing/basisless lots, and absent rail identity refuse with `credit_refund_basis_unavailable`. An operator must inspect independent original-payment evidence before arranging a repair; retrying alone does not establish it. The route accepts no caller-supplied proof or asset-basis override and never infers basis from timestamps, the installed SDK version, or current FX.

Refunds also require immutable DVM ownership evidence from the job, its verified retained receipt signed by the DVM's configured receipt key, or its durable terminal-report claim. A receipt with a valid signature under its own embedded key proves no DVM identity unless that key matches trusted server configuration. Without a configured receipt key, that receipt is ignored as ownership proof. Conflicting or absent ownership evidence refuses before accounting. The first accepted refund persists that owner on the draw, preserving later refunds after job retention. A refund-ID replay remains bound to that same configured DVM and survives receipt-key rotation through its persisted owner.

A successful positive funding records the current ledger sequence as an internal funding watermark without allocating a new sequence. Refund eligibility combines that order with drain balance-after and subsequent positive draws; free draws alone do not reopen a drained credit. The financial evidence export adds `draw_refunds` and these funding, ownership, and basis fields while excluding the request and free-text reason. For an active zero-balance credit, a latest non-released full drain with no evidence of later positive funding or activity is closed when the recorded funding watermark proves that order. It refuses with `credit_not_open`. If that watermark is absent and retained facts cannot distinguish closure from reopening, it refuses with `credit_refund_state_unavailable`. An operator must inspect independent funding and drain evidence before arranging a repair; retrying alone does not establish order. Proven reopened credits remain eligible, and exact refund-ID replay returns its original facts before either historical-evidence check.

Deploy the platform report endpoint first. Upgrade **every SDK process sharing the credit ledger and report outbox before issuing the first refund**, including retry workers. Pause monetary writes during this upgrade, and resume only after every ledger/outbox reader and writer uses the new version. Older funding writers do not maintain the funding-order watermark; mixed-version monetary writes after new metadata is first recorded require a state compatibility assessment before activation. Older processes do not recognize the new outbox kind or known-zero lot marker. Keep the upgraded readers while refund history and lots remain; an old process can misprice those lots. Rolling back to an older SDK after refund state exists requires an explicit state compatibility assessment. Additive schema changes alone do not make rollback or a mixed-version fleet safe. The schema additions are idempotent, and running initialization twice preserves recorded refunds. No caller protocol change is required: restored balance appears through existing credit status.

## Held Tempo drain operator decisions

The signed admin routes `/admin/credit/book-tempo-drain` and `/admin/credit/release-tempo-drain` add explicit immutable decisions for `pending` and `exit_required` Tempo session drains. They preserve the original held debit, the terminal compare-and-set boundary, and channel-before-credit locking. Booking attests the full off-path refund without manufacturing chain evidence; release restores the recorded value without reopening the channel or clearing its separate close-report obligations. The existing drain report wire shape is unchanged. Release additionally refuses non-final matching close intents unless the forecast is provably pending and both broadcast marker and transaction hash are absent. Legacy ready intents and current ready-but-not-yet-broadcast intents conservatively refuse until close/exit resolution. Any retained positive refund/payment fact also refuses release. Exact receipt zero and unknown are distinct. Payer-exit lower bounds never enter the exact amount: positive bounds retain only a sticky payment fact, while nonpositive bounds leave proof unknown. Monetary proof survives failed booking transactions and later missing reads. The admin list explicitly includes held write-offs while background payout lists retain their prior filter. Hosted bookings require the actual transactional reporter, and standalone reporting remains optional. Decision diagnostics add a labelled stable SHA-256 drain reference without exposing arbitrary caller IDs. Neither decision supports a partial amount. Request and response examples are in [the portable fixture](../protocol-fixtures/tempo-drain-decisions.json); validation, replay, and migration details are in [Hosting](HOSTING.md#held-tempo-drain-decisions).

## Terminal evidence

New job receipts keep schema version `1` and add optional signed `timing` with `accepted_at_ms`, `terminal_at_ms`, and cumulative `caller_wait_ms`. Acceptance and termination use Unix milliseconds; `issued_at` remains signing time in Unix seconds. Non-completed receipts also include SDK-derived `ended_by`: explicit caller cancellation and unanswered prompt/payment expiry are `caller`; handler failures, worker death, and idle expiry during processing or working are `provider`. Handlers cannot choose this attribution. Legacy receipts omit these fields and still verify. Jobs accepted before this change, including jobs still active during an upgrade, omit the additions and do not produce terminal reports because earlier caller waits are unknown; the SDK does not invent historical fault evidence.

Hosted servers with platform URL, token, DVM identity and durable database configured enqueue every terminal job, including free jobs, through the durable report outbox to `/_internal/job-terminal`. The payload contains the DVM/job identity, capability, outcome, attribution, payment-presence flag, timing and optional receipt sequence. It also carries draw settlement amounts and piece counts when known, but no caller identity, payment references, input, or output. The permanent deduplication claim and outbox insert commit together; startup and periodic recovery cover a crash after terminal persistence. Deliveries can repeat, so the platform deduplicates by DVM/job identity.

Deploy the platform endpoint before deploying report-emitting servers. These reports use the existing revenue transport policy: transport/5xx failures retry and abandon after 24 hours; 4xx responses, including 404, become permanently stale. The portable receipt and report contract is in `protocol-fixtures/job-terminal-evidence.json`; compatibility is tested with the pinned published `@dvmkit/sdk@0.1.5-rc.9` verifier.


## Tempo close terminal outcomes

A registered Tempo drain that cannot cooperatively close because its descriptor is invalid or its hosted retries are exhausted now returns HTTP 409 `tempo_channel_exit_required`, with `status: "exit_required"`, `drain_registered: true`, `drain_id`, and `channel_id`. Callers must use the channel's timed on-chain exit. A corrected credential does not reopen or debit that drain again. The debit remains reserved for the channel's refund; a late confirmed close can still fulfill it. Older callers that poll every 402 must handle this terminal 409. For a custom ledger without terminal-drain persistence, the 409 instead retains `status: "pending"` and explains that a corrected credential can retry when cooperative attempts remain. The portable response contract includes both modes in `protocol-fixtures/tempo-close-terminal.json`.

Completed Tempo drains remain readable when their credit is `unbacked`. Sweep-completed drains use the existing `sent` state and include `terminal_outcome` and `credit_unbacked` in their settlement evidence; caller liability is discharged only with sufficient refund evidence. Verified cooperative-close refunds now offset voucher headroom before any permanent loss row, credit status, or completion diagnostic is written. Missing proof defers classification while retaining finalized-channel spending restrictions and sweep retries. Partial refunds retain only the residual loss; verified payer exits retain only unpaid successful consumption, so unused voucher authority never adds a loss. Existing permanent losses are not reversed. The loss listing adds nullable decimal-string `refunded_to_payer_native` and `loss_native` fields, plus nullable `loss_basis` identifying cooperative receipt, payer exit, or caller assertion; old rows remain unknown, and financial export version 1 preserves exact new values and old schemas. See [Hosting](HOSTING.md) for the evidence and migration boundary.

Hosted report searches now stop in persisted `unmatched` after a definitive empty range and require an explicit operator retry. Automatic unproven loss-history discovery for the same hosted close honors that stop while retaining finalized spending restrictions and pending classification; known transactions and verified receipts remain usable. This does not discharge the payout obligation or authorize cleanup. See [HOSTING.md](HOSTING.md) for the retry API and recovery constraints.


## Custom credit store upgrades

Custom credit stores built against SDK 0.10.x must add `recordTempoDrainRefund` and `recordTempoDrainPayment` before they can complete held Tempo drains with this release. These optional interface members are required when the host has a matching open Tempo drain: the first retains exact cooperative refund amounts, including zero; the second retains positive payer-exit payment proof without inventing an exact amount. Advertising `tempoCreditLossEvidenceVersion: 1` alone is insufficient. A missing or failing writer leaves that channel finalized and pending for retry, without completing its drain or preventing unrelated channels from settling. Operator decision and cosmetic held-reason capabilities remain optional. See [Hosting](HOSTING.md) for the custom-store evidence and transaction contract.

## Compatibility and versioning

This is pre-1.0 alpha software. The public package API is exactly `@dvmkit/sdk`, `@dvmkit/sdk/server`, and `@dvmkit/sdk/testing`. `@dvmkit/sdk/internal` carries no stability promise, and deep `dist/` imports are unsupported.

Each public export has an explicit `@stability stable` or `@stability experimental` JSDoc tag on its named export declaration in the authored entry point. A tag on a grouped export applies to each name in that group. Root and testing exports start **stable**; server exports start **experimental**. Levels apply to the import path, so the same name can have different levels in different entry points. The [API reference](API.md) lists each level, and `check:api` records it in `api-surface.json` and refuses missing or invalid tags. Stable means covered by the compatibility promise below once its trigger occurs; it does not declare the package 1.0. Experimental exports can change without a deprecation window, but their signature changes still require release-note disclosure. Downgrading a stable export to experimental is itself a breaking change.

A breaking change makes a previously supported use stop working or changes its documented meaning. Examples include removing or renaming an export or removing its runtime value through a type-only export, changing parameters or return types, adding a required interface member, narrowing accepted inputs, changing defaults, error or payment semantics, or raising a runtime or dependency floor. Adding an optional facility is normally compatible. Shape checks cannot detect every semantic break: maintainers must review behavior and disclose it too. The signature guard conservatively requires disclosure for every signature difference, including compatible additions to an existing type.

The deprecation promise starts when **open sign-up begins or the first DVM built independently of dvmkit deploys, whichever happens first**. Record that event and its date in this section when it occurs; this policy does not assert that it has occurred. Until that trigger, breaking changes remain allowed with release-note disclosure. After the trigger, a replaced stable API must keep working for at least **two minor-version increments** after its replacement and deprecation ship. For example, an API deprecated in 0.26 remains working in 0.27 and can first be removed in 0.28. Publish the replacement, an `@deprecated` comment naming it, the deprecation version and earliest removal version in the release notes. Patch releases do not advance the window; a major release does not shorten it. Experimental APIs have no such window. Once the trigger has passed, every breaking release also ships a migration note in its release notes explaining what existing users must change. No migration guide is required merely to introduce this policy.

**Runtime support:** the package supports Node.js 22 and later (`package.json` declares `engines.node: >=22`). Running the TypeScript examples directly without compilation needs Node.js 22.18 or later for built-in type stripping. Contributor and release verification use the exact Node release in `.nvmrc`; that reproducibility pin is not the consumer support range. Security fixes target the latest published SDK release; there is no long-term support release or backport branch.

`npm run check:api` checks names, stability, and signatures against committed snapshots. Public signature differences and removals require a nonempty `### Breaking changes`, `### Breaking API changes`, or release-please `### ⚠ BREAKING CHANGES` section in the current release notes. During development that means `Unreleased`; for a bumped release version it means that version's section. A marker in an older release does not authorize a new break. This gate applies before and after the deprecation trigger, and it never substitutes for reviewing the deprecation window or semantic compatibility. See [release maintenance](RELEASING.md#api-snapshots) for updating the current snapshot and advancing the independent comparison baseline.

Wire compatibility with callers is separate from the package version and is declared per endpoint. A server built on this SDK answers `DVM-Protocol-Version: 1`, and an individual endpoint may require a set of named capability tokens the caller advertises, a minimum caller version, or both. Capability tokens are additive, so an endpoint that declares no requirement stays reachable by a caller that sends no compatibility headers at all. A caller that cannot meet what an endpoint declares gets HTTP 426 naming the required capabilities and, where one is declared, the minimum version. The protocol is specified at [dvmkit.com/docs/protocol](https://dvmkit.com/docs/protocol).


## Job credentials

An unauthenticated `POST /v1/job` returns a one-time `job_token` alongside the `job_id`. Callers must send it as the `X-Job-Token` header on subsequent status reads, message reads (JSON or SSE), message writes, and cancellation. A request with no credential gets a 401 `job_credential_required`; a wrong credential remains the opaque 404 `Job not found` response.

When a caller has lost its local job record, the standalone `@dvmkit/dvm-cli` can use the provider endpoint and token explicitly. Prefer environment variables so the bearer token does not enter shell history or the process list:

```sh
DVM_JOB_ENDPOINT=https://provider.example \
  DVM_JOB_TOKEN=<64-character-hex-token> \
  dvm status <job-id>
```

The same values are accepted as `--endpoint <url>` and `--job-token <hex>`. These overrides are request-scoped and are not saved; `dvm pay` still requires the local pending request and spending policy, so an endpoint and token alone cannot authorize a payment.

If an upgrade broke something for you, an [API compatibility report](https://github.com/dvmkit/sdk/issues/new/choose) is the most useful thing you can send us. It tells us which parts of the published surface people actually build on, which no test of ours can.


## Payment recorded before a snapshot failure

After a mid-job payment's accounting and inbound verification commit, a later snapshot failure returns HTTP 503 `job_snapshot_unavailable` with `payment_status: "recorded"`, `retryable: false`, and the `job_id` and inbound `seq`. Read the job status and messages instead of sending another payment. If the worker stopped, a non-payment message can resume the stored job using its accepted credit. An optional `credit` block retains the usual explanation of funds that did not apply to this job.

This is an additive error response for a failure that previously returned an unstructured 500. It does not change payment amounts, caller/request uniqueness, or funding and draw semantics. ## Unsigned paid calls

A DVM built with `secp256k1Auth({ allowUnsignedPaid: true })` advertises `/v1/info.auth` as `["secp256k1-schnorr-v2", "none"]`, signed scheme first, and also accepts an unsigned `POST /v1/job` when the job requires a per-call payment made with Cashu. This lets a standard HTTP payment wallet, which attaches a payment but never signs, call the DVM. Without the option the list stays `["secp256k1-schnorr-v2"]` and nothing changes.

A body whose structured input carries none of `pubkey`, `signature`, `timestamp`, `nonce` or `auth_statement` is unsigned. Any one of those fields makes the body signed, and it is verified exactly as before: a bad signature returns its `auth_error` and never falls back to the unsigned path. An unsigned body is validated against the capability schema without the envelope fields and runs as the anonymous requester, with the usual one-time `job_token` as its only handle for status reads, messages, mid-job payments and cancellation. The handler sees no `ctx.auth`. No replay entry is written; the payment's own replay protection stops reuse. An unsigned payer whose response is lost recovers the job, `job_token` included, by retrying with the same Cashu proofs, `X-Cashu-Request-Id` and body, under the binding described for [Cashu payments](#cashu-lock-requirements), or with the same token and body when it paid without a request id ([NUT-24 payment requests](#nut-24-payment-requests)); any other retry with an accepted payment is refused with HTTP 409 and returns neither the job nor its token. A signed caller's job never recovers for an unsigned retry, or the reverse. Hosting control's recovery, which requires the exact same payment artifact (see [Hosting](HOSTING.md)), is unchanged. If the job fails, released money lands on the shared anonymous requester, which no caller can claim.

Unsigned calls take Cashu, and exact x402 on a capability that sets `maxRuntimeSeconds` (see [Unsigned x402 payments](#unsigned-x402-payments)). With Cashu (NUT-24) the token is the payment, so a failed job keeping it is how Cashu payment already behaves. Tempo stays signed-only: a push-mode credential is already broadcast on chain when the DVM sees it, so the DVM cannot verify it, run the job and settle afterwards. A pull-mode Tempo credential could be held the same way, but the SDK does not yet restrict a challenge to pull mode. An unsigned request that needs payment but carries none gets an HTTP 402 `payment_required` challenge offering Cashu, plus x402 `accepts` on a capability that takes unsigned x402, with no Tempo `WWW-Authenticate` challenge and no prepaid-credit menu. No `/v1/quote` call is needed; `/v1/quote` stays signed-only. A dynamic-priced capability is priced from the unsigned input with the envelope fields removed, so its `onQuote` handler runs for anonymous callers with no caller pubkey. An unsigned request that resolves to no required payment, or reaches a DVM that offers no unsigned rail, receives the same `auth_error` a signed-only DVM returns, so free capabilities stay signed-only. An unsigned submit carrying an x402 payment (`PAYMENT-SIGNATURE` or `X-PAYMENT`) to a capability that does not take unsigned x402, or a Tempo credential (`Authorization: Payment`), is refused with HTTP 402 `payment_method_requires_signature` before any settlement or credit write, and so is an x402 or Tempo `payment` message on an unsigned job; pay with Cashu or sign the request. A mid-job `payment-request` on an unsigned job offers Cashu alone, with no `x402` or `tempo` option, because a push-mode Tempo wallet broadcasts its transfer before the DVM sees the credential and could not be refused in time. Signed callers keep every rail. An unsigned body carrying `credit_id`, `draw_id` or `fund` is refused with HTTP 400 `invalid_credit_fields`, and one carrying `request_id` with HTTP 400 `request_recovery_unsupported`: prepaid credit and request recovery belong to a verified pubkey. `POST /v1/credit` and balance-backed mid-job payments stay signed-only. A capability whose input schema is not a plain object schema stays signed-only.

### Unsigned x402 payments

A capability with `maxRuntimeSeconds` (whole seconds, 1 to 600) on a DVM with `secp256k1Auth({ allowUnsignedPaid: true })`, an `x402` block and Postgres takes exact x402 from unsigned callers the way a standard x402 server does: the authorization is verified with the facilitator before the job, and settled only after the job completes. A job that fails, is cancelled or is still running at `maxRuntimeSeconds` (the SDK aborts `ctx.signal` and fails it) never sends the authorization to the facilitator, so it expires unspent and the payer is not charged. The DVM holds the signed authorization in memory only; a process that loses it, by restart or because another machine holds it, cannot settle the job. It reports what the stored intent and the chain prove: an authorization not yet past its `validBefore` is left unresolved (the machine that holds it may still collect), one past it that was never submitted is released as unpaid, and one that was submitted is resolved from chain evidence. An unpaid job never delivers its output.

The 402 advertises `maxTimeoutSeconds` of `maxRuntimeSeconds` plus 30, and a payment whose signed `validBefore` is less than `maxRuntimeSeconds` plus 15 seconds away is refused with HTTP 402 `payment_authorization_too_short` before the facilitator is called. An authorization is single use: presenting it again, while its job runs or after, returns HTTP 409 `replay_rejected` and neither runs a job nor settles twice. The job's credit and draw are created at settlement, so `ctx.requestPayment` throws, `ctx.prompt` rejects, and `ctx.sendMessage("prompt", ...)` or `ctx.sendMessage("payment-request", ...)` throws on these jobs. `PAYMENT-RESPONSE` is not on the `202` because settlement follows the job; it appears on the response that first reads the job once settled (the submit response when the job finishes in the same request, otherwise `GET /v1/job/:id`).

The output is withheld until the settlement succeeds. From admission, `summary`, artifacts and every message are absent from `GET /v1/job/:id`, `GET /v1/job/:id/messages` (JSON and SSE) and the submit response, and each carries `content_available: false` with `content_withheld: "payment_pending"`. There is no mid-run streaming: a message stream opened while the job runs closes empty. A job whose handler finished but whose settlement is still running reads as `processing`. Once the facilitator settles, the job reads `completed` with its output and `PAYMENT-RESPONSE`. If the settlement is refused, for example because the payer cancelled the authorization or moved the funds, the job reads `failed` with `content_withheld: "payment_unsettled"`, the output is never served, its signed receipt reports nothing paid, and `onJobTerminal` reports `paid: false`. An unknown settlement outcome keeps the output withheld, reports nothing as unpaid, and the next read of the job retries it. A facilitator call is bounded by `x402.facilitatorTimeoutMs` (default 10000): a `/verify` that times out refuses the payment, and a `/settle` that times out is unknown, never refused. A facilitator answer of `settlement_pending` keeps its transaction hash and is resent once with the identical authorization; still pending afterwards is unknown. A submitted authorization the chain shows used settles the job on a later read; one the chain proves unused, once the chain is past its `validBefore`, ends unpaid; a failed chain read leaves it unknown until `reconcile` or a later read resolves it. A cancelled or failed job keeps only its cancellation message. Callers who need streaming should use a signed request with prepaid credit.

A payer may have one authorization outstanding at a time: a second one from the same `from` address while the first job is still running is refused with HTTP 429 `x402_payer_busy` before the job starts, because the facilitator's verification reserves no balance and parallel authorizations from one wallet could not all be paid. An authorization past its `validBefore` no longer counts, whatever state it was left in. Custom `X402ExactSettlementStore` implementations enforce the limit through `claim`'s `maxOutstandingPerPayer` option; a store that ignores it does not. Capabilities without `maxRuntimeSeconds`, and long, multi-step or metered jobs, stay signed-only for x402.

### The x402 channel route

A capability offered on the x402 channel (`channels: { job: false, x402: {} }` or `{ job: true, x402: {} }`) is served to stock x402 clients at `POST /v1/x402/<capability>`, one request per call, with an x402 rail and Postgres. The rail may come from `DVMConfig.x402`, the host's `x402` option, or the host environment (`DVMKIT_X402_PAY_TO` and related variables); the descriptor need not set it. Direct `createDVMServer` callers supply the resolved rail through its `x402` option. The route needs no `auth` scheme, takes the definition's input as the flat JSON body, and runs the job through the same unsigned deferred-x402 path described above, so withholding, receipts, `onJobTerminal` and the settlement store behave the same. A name not offered on the x402 channel answers 404 `unknown_capability`, and `/v1/job` answers its usual `unknown_capability` for an x402-only name. A DVM may offer every capability on x402 alone; `/v1/info` then lists no capability and `/v1/job` and `/v1/quote` point callers to the route.

An unpaid request gets HTTP 402 with `PAYMENT-REQUIRED`, quoted from its body. On a capability with a `listing`, an empty body or one that fails the input schema (a discovery validator sends `{}`, or the listing's example) is quoted from `listing.example` and runs nothing; without a listing it answers 400. A paid request whose body fails the input schema answers 400 before the facilitator is called. A body carrying `pubkey`, `signature`, `timestamp`, `nonce` or `auth_statement` answers 400 `signed_fields_not_accepted`, and `ctx.auth` is never set on this channel. Only an unsigned x402 payment (`PAYMENT-SIGNATURE`, or `X-PAYMENT` where the facilitator supports v1) is accepted: `X-Cashu` or an `Authorization: Payment` credential answers 400 `payment_method_not_accepted` with a hint pointing to `/v1/job`.

The 402's `resource` is the DVM's public origin (`DVMKIT_PUBLIC_URL`; only in `devMode` the request's origin), then the prefix a host mounted the DVM under, if any, then `/v1/x402/<capability>`; a query string or another spelling of the path is never echoed into the challenge or sent to the facilitator.

A capability with a `listing` declares it for x402 catalogs, such as the Bazaar discovery extension, on the v2 `PAYMENT-REQUIRED` header only. The header's `resource` gains the listing's `description`, `mimeType: "application/json"` and any `serviceName`, `tags` and `iconUrl`, and its `url` is the route's own address above, or `listing.resourceUrl` when one is set. `extensions.bazaar` describes a `POST` with a JSON body, the listing's `example` and the route's flat body schema (no signed-request fields), and any `outputExample`. Payment stays bound to the route's own address: each v1 requirement's `resource` is that address even when `resourceUrl` is set. The v1 JSON body carries no listing, and an unlisted capability declares only the `url` and `mimeType`. Whether a catalog shows `iconUrl` is the catalog's choice. The listing is fixed in [`protocol-fixtures/x402-listing-v1.json`](../protocol-fixtures/x402-listing-v1.json).

A stock client echoes the 402's `resource` and `extensions` in its paid retry, and catalogs list a resource from the payload the facilitator receives. The server therefore replaces both with its own before every verify and settle call, so whatever a caller puts there never reaches the facilitator. On the route a v2 payload carries the 402's `resource` and, for a listed capability, its `extensions`. Every other exact payment, on `/v1/job` (deferred or upfront), `/v1/credit` or a mid-job top-up, carries the resource the server bound the payment to and no `extensions`. A reusable-channel (`batch-settlement`) payment on `/v1/credit` carries `resource.url` `/v1/credit` and no `extensions`, including when a recorded settlement is resent during recovery. A v1 payload carries neither field. A facilitator may answer verify or settle with an `EXTENSION-RESPONSES` header, base64 JSON reporting each extension's status, such as `{"bazaar":{"status":"processing"}}`. The server logs every status it reports, up to eight extensions per answer with a count of the rest, including a rejection's reason, and never returns the header to callers. `processing` is the usual answer on both calls, and a missing `success` is not a failure. Every `PAYMENT-RESPONSE` and `X-PAYMENT-RESPONSE` the server sends carries only `success`, `transaction`, `network`, `payer` and an `errorReason` of at most 128 characters from the facilitator's settle answer; its `errorMessage`, `extensions`, `amount` and any other field stay server-side. That holds on the route, on the one a later `GET /v1/job/:id` repeats for a deferred x402 job, on upfront exact payment on `/v1/job`, on a payment recovered from a stored settlement, and on `/v1/credit`. A reusable-channel (`batch-settlement`) answer on `/v1/credit`, for funding or a drain, also keeps `extra.channelState`, which the payer's client reads to advance its channel record, reduced to `channelId` (a 32-byte hex id, which must be the payment's own voucher channel, compared case-insensitively) and any of `balance`, `totalClaimed` and `chargedCumulativeAmount` (decimal unsigned integers no larger than 2^256 − 1); a channel state that fails those checks is dropped whole and logged as `x402_settle_channel_state_dropped`. The SDK's paying client applies the same channel binding before it persists an answer, since a client keys channel records by the answer's `channelId`.

`/v1/info` lists capabilities offered on the x402 channel under `x402_capabilities`, keyed by published name, apart from the `capabilities` map, which is unchanged and holds only the `/v1/job` definitions. One name may be a different definition on each channel, such as an x402 `fetch` beside a `/v1/job` `fetch`. Each entry has the `capabilities` entry shape, with the route's flat body schema as `input_schema` and the x402 definition's price, plus `url`, the route's address including the host's mount prefix. `url` is always where to call the route, even when a listing's `resourceUrl` names another address for catalogs. A mount prefix contributes itself less one trailing slash, matching where the route is served: `/feed/` contributes `/feed`, and `/feed//` contributes `/feed/`. The key is absent when no capability is offered on x402. The shape is fixed in [`protocol-fixtures/x402-info-v1.json`](../protocol-fixtures/x402-info-v1.json).

A paid request is answered once, within one budget measured from its arrival: the capability's `maxRuntimeSeconds` for verification and the handler, then `x402.facilitatorTimeoutMs` (default 10000) for settlement. The handler is stopped when that bound runs out, so the time verification took counts against it, and a request whose verification used the whole bound runs nothing. A settlement starts only while a full facilitator timeout remains, so an authorization not yet sent by then is released and the request answers 503. A gateway that stops waiting for response headers before this deadline answers 504 while the job may still finish and settle, leaving the caller charged without the result or a `job_token`; when `DVMKIT_X402_RESPONSE_LIMIT_MS` is set, the server refuses to start (in `devMode`, logs `x402_route_response_limit_exceeded`) if any x402 capability's `maxRuntimeSeconds` × 1000 plus its facilitator timeout exceeds it. The answers are:

| Case | Status | Body | Headers |
| -- | -- | -- | -- |
| Completed and settled | 200 | `status: "completed"`, `charge_outcome: "charged"`, `job_token`, and `messages` when their serialized UTF-8 array is at most 1,048,576 bytes; a larger result keeps `payload_in: "messages"` for `GET /v1/job/:id/messages` | `PAYMENT-RESPONSE`, `X-PAYMENT-RESPONSE`, naming the transaction and network |
| Handler failed | 500 | `status: "failed"`, `reason`, `display`, `hint`, `charge_outcome: "not_charged"` | none; nothing settled |
| Handler failed, marked as the caller's | 422 | the same | none; nothing settled |
| Runtime bound hit | 503 | the same | none; nothing settled |
| Completed with no time left to settle | 503 | the same, with a `display` saying the work finished and the result was withheld | none; nothing settled |
| Settlement refused | 402 | `error: "x402_settlement_refused"`, `display`, `hint`, `charge_outcome: "not_charged"`; no `messages`, no `job_token` | `PAYMENT-RESPONSE` with `success: false` |
| Authorization lost (fail-safe) | 402 | `error: "authorization_unavailable"`, the same fields | `PAYMENT-RESPONSE` with `success: false` and `errorReason: "authorization_unavailable"` |
| Outcome unknown at the deadline | 202 | `status: "processing"`, `job_token`, `content_withheld: "payment_pending"`, `charge_outcome: "unknown"`, a hint not to pay again | `Retry-After` |

A handler that calls `ctx.fail(reason, { callerFault: true })` says the caller's own request caused the failure, such as a URL the service refuses, a page that does not exist or a paywall. The route answers that failure 422 instead of 500, so the caller sees a 4xx instead of a 5xx. 422 rather than 400 because the request was well formed, paid and run, while the x402 v2 HTTP transport reserves 400 for an invalid or malformed payment payload, and this route answers 400 to a body refused before anything ran. The route never settles a failed job, whatever the status, so the caller is not charged. The mark is stored on the job's final `cancel` message as `caller_fault: true`, which a `/v1/job` caller also reads; there a failed job's response is unchanged. The mark counts only on a provider's message: a requester's own cancel carrying `caller_fault` is ignored. A failure that ran out of runtime keeps its 503, and without the mark a failed handler answers 500 as before. `{ refund: true }` has no effect on the job and is not recorded on it; the test context from `@dvmkit/sdk/testing` still exposes it as `refundRequested`.

The authorization-lost row is defensive: the process serving a request holds its authorization until settlement resolves it, so the row answers only an authorization lost some other way. A 202 caller reads `GET /v1/job/:id` with the `X-Job-Token` header after `Retry-After`; that read retries the settlement and returns the result once it lands. 502 and 504 stay reserved for gateways. A wallet with a job already running gets 429 `x402_payer_busy` with `Retry-After` (the bound plus the settle timeout) and a hint. Every response that names a job carries the `DVM-Job-Identity-V1` header, and the route's CORS exposes `PAYMENT-REQUIRED`, `PAYMENT-RESPONSE`, `X-PAYMENT-RESPONSE` and `Retry-After`. The rows are fixed in [`protocol-fixtures/x402-route-v1.json`](../protocol-fixtures/x402-route-v1.json).

When `DVMConfig.x402` is set, configuration checks the listing's challenge size immediately; otherwise that size check waits for the host to resolve the rail. Listing and input validation still run at configuration. The server checks the route's challenge at boot with its real public origin (`DVMKIT_PUBLIC_URL`), the host's mount prefix, the route's timeout and a fixed price, and refuses to start when the encoded `PAYMENT-REQUIRED` header would exceed 7 KiB. It also refuses to start when the payment methods it was given, including a host-level `paymentMethods` override, leave out `"x402"`, or, outside `devMode`, when `DVMKIT_PUBLIC_URL` is unset or not an http or https URL: a request's origin comes from its caller-chosen `Host` header, and the resource reaches the facilitator's settlement. It also refuses to start, or in `devMode` logs a warning and starts, when the route could not take a payment: the DVM prices in a currency other than USD, `x402.dualServe` is `false`, or the server has no durable x402 settlement store (no Postgres), where every paid request would answer 503 `x402_not_offered`. A server with no x402 rail at all, from neither its `x402` option nor the host's options, environment or mounted DVM, is not refused for that: it starts, logs one `x402_rail_missing` warning naming the capabilities affected, answers each of their routes 503 `x402_not_offered` with a hint that x402 is not configured, never a 402, and leaves them and the x402 payment method out of `/v1/info` and `/v1/quote`, so its `/v1/job` capabilities and other rails keep serving. The checks that do not need the rail still run, the pricing currency and the `DVMKIT_X402_RESPONSE_LIMIT_MS` deadline (at the default facilitator timeout) among them, so a rail configured later cannot stop the DVM booting. A descriptor whose own `DVMConfig.x402` was not passed to `createDVMServer` is still refused.

### Refund-locktime floors

`/v1/info.cashu.min_locktime` is the shortest refund `locktime`, in seconds from now, a caller should lock to; the DVM enforces it less 24 hours so a caller resuming an unacknowledged payment still clears it. It is 604800 (7 days) unless the builder sets `cashu.minLocktimeSeconds` in `configureDVM`, as a whole number of seconds of at least 90000 (25 hours), so the enforced floor always lies at least an hour ahead.

A NUT-24 wallet cannot be told this value: the payment request carries no `locktime`, and a wallet such as Nutshell locks a refund path to itself opening after 24 hours by default. A builder who wants to take those payments sets `cashu.unsignedMinLocktimeSeconds`, a whole number of seconds of at least 3600, enforced exactly with no margin, because such a wallet never resumes a payment. A DVM that sets a `cashu` block and serves unsigned paid calls (no auth, or `allowUnsignedPaid`) advertises it as `/v1/info.cashu.unsigned_min_locktime`; otherwise the field is absent and the unsigned floor is `cashu.min_locktime` minus 24 hours. `configureDVM` throws on a value outside either rule.

Which floor applies depends on how the payment arrives, not on the kind of DVM:

| Payment | Floor |
| --- | --- |
| `POST /v1/job` with no signature and no `X-Cashu-Request-Id` (a NUT-24 wallet), on a DVM without auth or with `allowUnsignedPaid` | unsigned: `cashu.unsigned_min_locktime` seconds after receipt |
| Any `POST /v1/job` carrying `X-Cashu-Request-Id`, signed or not, on any DVM | signed: `cashu.min_locktime` minus 24 hours |
| A signed `POST /v1/job`, a mid-job `payment` message, `POST /v1/credit` | signed |

A payer that sends `X-Cashu-Request-Id` reads `cashu.min_locktime` before locking and may re-send the same payment after a lost response, so it keeps the 24-hour margin even on a DVM without auth. Because the header picks the floor, an unsigned payer always gets the shorter of the two, so `configureDVM` refuses an `unsignedMinLocktimeSeconds` longer than `minLocktimeSeconds` less 24 hours. A `lock_not_exclusive` refusal's `hint` names `cashu.unsigned_min_locktime` only on the unsigned path of a DVM that advertises it.

A floor shorter than the default is safe only if the builder melts banked proofs more often than the floor. Banked proofs wait unswapped for the batch melt, and once a proof's `locktime` passes and it is still unmelted, NUT-11 lets the payer take it back through its `refund` key, or, when the proof names no `refund` key, lets anyone holding the proof spend it. The accumulator monitor's `wallet_accumulator_batch_expiring_soon` event fires 36 hours before a batch's earliest locktime, or at half the shortest enforced floor when that is shorter, so a payment at the floor does not raise it on arrival.


## Job identity field

Every 200 or 202 response to `POST /v1/job`, `POST /v1/request-resume/:id` and `POST /v1/request-result/:id` carries a `DVM-Job-Identity-V1` response-head field whose value is the body's `job_id`, byte for byte, so a router or caller can learn which job a response names without reading a body of any size. No other status carries it. The value grammar is `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`; a server whose job ID falls outside it sends no field. A reader takes the value from `Headers.get`, trims nothing and never folds case: a repeated field (joined with `", "`), an empty value or any other character is invalid, and a trailer of the same name is never identity. The portable contract and its classification vectors are in `protocol-fixtures/job-identity-v1.json`. Hosting control's status reports `jobIdentityHeader: "v1"` when the deployment emits the field.


## Per-job costs

A handler can declare what a job cost **you**, the builder, to serve — a vendor API call, a GPU minute, a per-request licence fee — and the SDK reports it to the platform alongside what the caller paid, so your dashboard can state a margin instead of guessing at one.

```ts
const transcript = await ctx.step("transcribe", async () => {
  const result = await whisper(audio);
  ctx.cost({ amount: result.seconds * 0.0001, currency: "usd" });
  return result;
});
ctx.artifact({ mime_type: "text/plain", data: transcript.text });
```

`amount` is in whole currency units, like every other money figure you hand the SDK. Call it once per cost you incur; the declarations for one job are summed, and only the total is rounded, to a millionth of a unit. That ordering is what makes fine-grained declarations safe: a per-token charge of $0.0000003 is below the reported resolution on its own, but a thousand of them still add up to $0.0003 rather than to nothing. Every call in a job must name the same currency.

Three things worth knowing:

- **Declaring nothing is not declaring zero.** A job whose handler never calls `ctx.cost` reports no cost at all, and the dashboard says the margin is unknown rather than showing it as 100%. `ctx.cost({ amount: 0, currency: "usd" })` is how you say a job genuinely cost you nothing.
- **Declare the cost where you incur it, including inside `ctx.step`.** The step cache carries those declarations with the result and applies them once when a replay skips the body.
- **Every terminal job reports its declared cost.** A paid completion, or a failed or cancelled job whose draw settled for its finished pieces, carries the cost on its revenue report. Any other free completion, failure, or cancellation sends a separate cost-only report and does not create revenue.

The cost is yours, never the caller's: it is recorded separately from what the caller paid and is never netted against it. Both report shapes use the same durable outbox. Cost-only reports are keyed on the job id and revisioned, so retries and cross-machine updates converge on the latest cumulative value. With the Postgres job store, boot-time and periodic reconciliation enqueue any terminal cost revision that a process exited before reporting, and book any terminal job whose settled credit draw never reached the revenue outbox; the recovered revenue report is identical to the in-line one, so the platform deduplicates it. Other job stores get no reconciliation: their cost-only report is durable only once the outbox insert commits, so an exit between the terminal save and that insert loses it.


## Rate cards

A priced capability can tell callers what it charges per unit, so an agent can explain the price before it asks for a quote. Declare `rates` next to `price` or `onQuote`, in the flat shape or on an entry in `capabilities`:

```ts
capabilities: {
  synthesise: {
    onQuote: { schema, handler: quoteBySize },
    rates: [
      { label: "balanced", amount: "0.00015", currency: "USD", per: "character" },
      { label: "expressive", amount: "0.00030", currency: "USD", per: "character" },
    ],
    onJob,
  },
},
```

`/v1/info` publishes the list as `capabilities.<name>.pricing.rates`, exactly as you wrote it: same order, same strings. A capability without `rates` publishes nothing extra. For a quoted capability the rates describe how your quote is computed; the SDK does not compute or check quotes against them, so keep the two in step yourself.

The server refuses to start, naming the capability and the entry, when a rate card breaks one of these limits:

- 1 to 5 entries, on a capability with `price` or `onQuote`. A free capability cannot declare rates.
- `amount` is decimal dollars as a string, above zero and at most 12 characters: `"0.00015"`, not `0.00015` or `"$0.00015"`.
- `currency` is `"USD"`.
- `per` names the unit (`"character"`, `"episode"`, `"GB per day stored"`) and `label`, which is optional, names a tier. Each is 1 to 24 characters with no leading or trailing spaces.
- No other keys.

The [portable fixture](../protocol-fixtures/capability-rates.json) carries the same limits and the accepted and refused examples, for clients that parse the field.

## Terminal reads and receipt recovery

A streamed `complete` can precede durable finalization. Job status reads, submit responses, and request recovery responses wait for terminal work and receipt repair for up to two seconds, in addition to ordinary store and response-metadata reads. Terminal status and result fields come from the stored snapshot; an unfinished save leaves the last committed nonterminal state visible.

Before settling a completed job's pending credit draw, the SDK drains outgoing messages in order and commits its terminal snapshot. Failed outgoing appends and terminal snapshot writes retry for up to 30 seconds, with 500 ms between failed attempts. An outstanding store operation must finish or time out before another attempt; the retry budget does not cancel an in-flight database transaction. Stable append identities prevent a lost acknowledgement from duplicating a message or payment-request counters. The built-in Postgres and memory stores retain append identities across terminal log cleanup. Custom streaming stores must honor `AppendOutgoingOptions.appendId` with the same durable deduplication semantics.

If that budget expires without a committed terminal winner, completion becomes `failed` with reason `terminal_persistence_failed`, and the pending draw is released rather than settled. The built-in stores atomically save this failure and its final cancel message. If storage remains unavailable, the owning process retries recording the failure and resolving its draw when storage returns; a process that dies before committing a terminal result leaves the existing stale-job recovery to release its hold. A refusal on healthy storage releases its draw through the same terminal funnel, preserving its own reason even if an earlier step write failed. A competing durable cancellation or failure remains the terminal winner.

Receipt persistence may lag settlement once the complete result is durable. On a terminal response from a provider with receipt support, `receipt_pending: true` explicitly reports that the signed receipt is not yet durably stored. It is omitted once `receipt` exists, and providers without receipt support omit both. The portable example is `protocol-fixtures/job-receipt-pending-v1.json`. Read the same job again; a pending receipt never requests another submission or payment.

Any later reader, including a fresh process after restart, can issue the missing receipt from the committed terminal result and recorded draw. A settled draw is read without invoking settlement again. Concurrent issuers reuse the job's claimed receipt sequence and return the same write-once stored bytes. Failure and cancellation resolve pending draws idempotently, settling finished pieces and releasing the rest; their stored status and receipt outcome agree. This adds an append-deduplication table to Postgres without changing receipt signing bytes. It does not reconstruct output lost before this version or before a terminal commit.


## Card drain recovery

Card drains add `refund_blocked` for permanent refusal and `written_off` for an operator's closure of the unpaid remainder. Both remain readable through the original drain id. Blocked refunds retain the debit and remain liabilities, but polling does not retry them; clients should direct the caller to the service operator. Replanning immediately retries the unpaid portion while retaining completed allocations. Caller responses expose structured recovery amounts and failure codes without operator reasons. The signed admin request/replay contract is in [the card-drain fixture](../protocol-fixtures/credit-drain-stripe-v1.json) and operational guidance is in [Operating](OPERATING.md#blocked-card-refunds).

Postgres initialization adds nullable `credit_drains.card_recovery` without rewriting old plans. Missing entry revisions mean revision zero and retain their original idempotency keys. A replan persists its revision and retained successes before planning or sending replacements, so a crash resumes the same revision without treating a partial retained plan as complete. Money amounts remain integer micro-units/cents. A write-off stores separate refunded gross and unpaid amounts; it emits no `sent` receipt or successful-refund report. Full successful refunds retain the transactional drain/outbox contract.

Custom card ledgers must supply `withCardRefundLock`, `saveCardDrainState`, and `saveCardRefund`; a missing capability fails closed before refunds. The lock must serialize all refund and recovery work per credit across machines, re-read under that lock, and release on failure. The callback's optional query connection is session-scoped: plan and progress writes autocommit; booking and the outbox share a short transaction. Implementations must honor `tx` on drain reads, plan/state writes, funding-lot reads, terminal transitions, and receipt appends to avoid pool exhaustion. State writes compare expected status/revision, and progress writes refuse obsolete revisions. Other rails need no recovery methods.
