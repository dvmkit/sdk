# Hosted admission and draining

Hosting control is opt-in. Pass `hostingControl: { secret, scope }` to `createDVMHost` or `createDVMServer`, or set both `DVMKIT_HOSTING_CONTROL_SECRET` and `DVMKIT_HOSTING_CONTROL_SCOPE` for a hosted `createDVMHost` boot. Supply a dedicated random secret of at least 32 bytes, a stable deployment scope, `DVMKIT_DVM_ID`, and Postgres. A partial environment configuration fails boot. Do not reuse caller authentication keys, builder signing keys, or payment credentials. Configured scopes start closed: the management client must fund and sign a finite lease before the first payment. Without this option, self-hosted admission behaves as before and the control routes are absent.

The management client sends JSON to `POST /_hosting/control` with `action: "drain"` or `"resume"`. It sends JSON to `POST /_hosting/status` with `action: "status"`. Every body contains `scope`, `dvmId`, `timestampMs` (Unix milliseconds, within five minutes), and a fresh 16–128 character URL-safe `nonce`. A transition also contains a positive, monotonically increasing integer `generation`. Drain additionally contains `deadlineMs`, no more than 24 hours in the future. Drain and status keep the version-one signature: UTF-8 JSON of `["dvmkit-hosting-v1", action, scope, dvmId, generation ?? null, deadlineMs ?? null, timestampMs, nonce]`.

Resume **requires** `version: 2`, `leaseExpiresAtMs`, and `deadlineMs`. Both are Unix milliseconds. At the locked PostgreSQL time, the lease must be in the future and no more than one hour away; the completion deadline must be later than lease expiry and no more than one hour after it. The platform may use a shorter funded window, such as five minutes of admission and one hour for work already accepted. Version-two signed bytes are UTF-8 JSON of `["dvmkit-hosting-v2", action, scope, dvmId, generation ?? null, leaseExpiresAtMs ?? null, deadlineMs ?? null, timestampMs, nonce]`. Set `X-DVM-Hosting-Signature` to the lowercase hex HMAC-SHA256 returned by `signHostingControl(secret, body)` from `@dvmkit/sdk/server`. A captured nonce cannot be reused, even for a status read. Retry the identical generation, lease expiry, and completion deadline with a fresh nonce to get the current result while the lease remains valid. A stale generation, same-generation change, expired lease, or legacy unbounded resume returns 409.

The status body contains `state` (`accepting`, `draining`, or terminal `closed`), `generation`, `leaseExpiresAtMs` (or `null`), `deadlineMs` (or `null`), `activeJobIds`, `unownedActiveJobIds`, `pendingAdmissionCount`, `pendingAdmissions`, `unresolvedAdmissionCount`, `unresolvedAdmissions`, and `jobIdentityHeader`. `jobIdentityHeader` is `"v1"`: the deployment states each accepted job's ID in the `DVM-Job-Identity-V1` response-head field of its job submit, resume and request-result successes. `activeJobIds` contains only jobs admitted under the signed deployment scope. `unownedActiveJobIds` contains active jobs for the DVM ID that have no hosting admission under any scope, such as jobs created before hosting control was enabled. They are not automatically adopted or cancelled: another deployment may own them. Treat a nonempty unowned list as unresolved shutdown work and migrate each job only after identifying its deployment owner. Jobs admitted under another scope appear in neither list. The admission arrays carry durable admission and work IDs. All values come from Postgres and are shared by every instance. A pending admission was reserved before drain but has not finished verification or job persistence. An unresolved admission reached a payment verifier, which may have moved money, without a confirmed job. Treat it as recovery work; do not infer that no payment landed. When a matching job or funding record becomes durable, status resolves that admission. The existing payment and credit recovery paths remain available while draining.

New `/v1/job` submissions and fresh `/v1/credit` funding reserve admission under the scope row lock before payment verification. The SDK checks PostgreSQL time **after** obtaining that lock. Expiry atomically closes the gate and pins the completion deadline for admissions already in flight; a process restart or missed control call cannot reopen it. Existing accepting rows without a lease migrate closed and retain their accepted, pending, and unresolved work with a one-hour recovery deadline. An unleased row written by an older instance during a mixed-version rollout closes the same way when the new SDK next reads it. An already reserved submission may finish after admission closes; if a job persists after its deadline, the SDK cancels it before dispatch. Once the deadline passes, every instance sweeps scoped active persisted jobs to provider-attributed durable terminal cancellation, releases pending credit draws through the existing terminal path, emits a receipt when configured, and signals the running handler's `AbortSignal`. A later funded resume does not erase a prior run's deadline. Status, result, balance, refund, reclaim, and recovery of already recorded funding remain available. The one-second sweep cadence is not a healthy-job runtime limit; a job may run indefinitely while admission stays open under renewed leases.

A retry carrying the exact payment artifact of an accepted hosted job can recover that same job during drain without another rail verification. The SDK matches the artifact hash against its durable admission record, then checks the original request fingerprint and caller identity before returning the saved job token. A new artifact or changed request cannot use this recovery path. Signed public request-ID resume and recorded credit-funding replay also remain available.

Handlers should observe `ctx.signal` and stop their own work promptly. A handler can ignore abort, and an external API call may already have happened. Terminal cancellation prevents later SDK completion and keeps the caller's durable job and credit outcome truthful; it cannot undo effects outside the SDK. Reconcile any unresolved admission before shutting down the last machine that can observe its payment provider.

Terminal cleanup uses `POST /_hosting/closure` with `action: "close"`, then `POST /_hosting/closure-certificate` with `action: "certificate"`. Both commands require `version: 3`, the original `dvmId` and `scope`, the closure’s `generation`, a stable 16–128 character URL-safe `operationId`, a fresh `timestampMs` and `nonce`, and `X-DVM-Hosting-Signature`. The first close uses a generation strictly newer than the current control generation. Sign UTF-8 JSON of `["dvmkit-hosting-closure-v3", action, scope, dvmId, generation, operationId, timestampMs, nonce]` with HMAC-SHA256 using the hosting-control secret; `signHostingClosure` from `@dvmkit/sdk/server` produces the signature. A repeat close may reuse the same operation and generation with a fresh nonce. Closure is terminal for that scope: neither an older client nor a later lease can resume admission. The certificate response binds the original DVM and scope, persisted SDK instance ID and boot epoch, operation, generation, and database cutoff transaction. A restart changes the boot epoch and invalidates an older certificate.

`complete: true` and `eligible: true` require a sole managed mount, durable job/credit/replay/report stores, known rail stores, no pending or uncertain admission/payment/report/settlement, and zero caller balances and unresolved refund liabilities in every recorded currency. Unknown or unpriced facts refuse eligibility. Pending x402 payout batches also block. The SDK retains credit, job, and refund history and keeps recovery available after closure; a paid original Lightning invoice can still be credited or repaired under its persisted invoice and original admission. A pre-migration invoice without admission can be credited or repaired only when its database observation predates the closure cutoff, and it permanently blocks a positive cleanup certificate because its original ownership is unknown. A multi-mount host continues serving but cannot enter terminal cleanup or receive a positive certificate because its historical credit ledger cannot safely assign every row to one mount. Legacy unowned work and an ambiguous late payment also prevent certification. Tempo charge reservations persist before broadcast and remain unresolved until a matching durable payment marker is booked; an uncertain broadcast cannot be treated as unpaid. A used x402 or Tempo channel can support a positive certificate only when its original chain and contract binding and complete local history are known, its original claims, refunds, closes, and payout reports are discharged, and the configured RPC provides matching finalized chain state and receipts. The SDK checks that evidence against the same closed operation and unchanged local obligations before persisting or returning it. Missing historical provenance, including a channel table that predates history tracking even if it is empty, pending or ambiguous effects, and unavailable or conflicting chain evidence remain ineligible; an old zero-balance snapshot is insufficient. This is cooperative evidence about SDK-owned obligations, not proof that a hostile builder has no hidden liabilities. The platform must separately prove its supplier and wallet obligations before deleting a resource.

A hosted Tempo close stops cooperative attempts after three retired reservations (four broadcast attempts). Its final report obligation becomes `exhausted`, and its drain becomes `exit_required`. The caller receives HTTP 409 `tempo_channel_exit_required` and must use the timed on-chain exit. The debit and close intent remain intact: restoring spendable credit while an old close might still land could pay the same balance twice. An exhausted obligation remains watched for chain finalization. A late receipt or recovered cooperative close claims that terminal row and sends the payout report once; a confirmed payer exit resolves it to `no_report`. Cleanup remains blocked until that evidence arrives.

Missing, malformed, mismatched, or conflicting channel descriptors also make the registered drain terminal `exit_required`, before reserving a report or broadcasting. The catalogued `tempo_session_close_descriptor_refused` event carries the channel, the caller's amount at stake in native token units and currency micro-units, and the refusal. Sending a corrected descriptor under that drain ID returns the same timed-exit instruction without another debit or broadcast. Its funds remain in the channel, the close intent prevents reuse, and the caller recovers them through the timed exit. A concurrent close that already landed can still fulfill the drain from chain evidence.

A definitive search that exhausts the reservation-time range or reaches block zero without evidence makes the report obligation terminal `unmatched`. Automatic report-history searches stop. A separate unresolved caller refund can still be checked by the drain sweep. `tempo_session_close_recovery_unmatched` carries the channel, obligation, and potential builder payout in native token units. This state continues to block cleanup with `settlement_reports_unresolved`: terminal search failure is not proof that the builder received no payment, so deleting the report history would risk losing its payout report. `tempo_session_close_attempts_exhausted` also carries the channel and potential payout. Both events use decimal strings for native amounts. Searches paused at their per-pass budget keep their existing cursor and continue on the next poll.

After repairing incomplete RPC history, explicitly reopen an unmatched report search with the supported server function. Use the original deployment identity and the obligation ID from the event; the database pool is the same pool configured for that deployment:

```ts
import { retryHostedTempoCloseReport } from "@dvmkit/sdk/server";

const reopened = await retryHostedTempoCloseReport({
  db, dvmId, scope, obligationId,
});
```

The function returns `true` only when it changes an owned, unsubmitted `unmatched` or `no_report` close obligation back to `reserved` and clears its search cursor. The next session sweep or hosting closure check searches from the chain head. It does not broadcast or reopen the caller's drain. An active, submitted, delivered, foreign, or competing report is not reopened. Keep this database operation in an operator process with deployment database access; do not expose it as an unauthenticated HTTP handler.

When escrow history is permanently unavailable, the operator can explicitly forgo an owned, unsubmitted `unmatched` builder payout report:

```ts
import { writeOffHostedTempoCloseReport } from "@dvmkit/sdk/server";

const writtenOff = await writeOffHostedTempoCloseReport({
  db, dvmId, scope, obligationId, note: "Escrow history is irrecoverable",
});
```

This returns `true` only for the transition from `unmatched` to `no_report`; every other state, submitted report, foreign identity, and repeat call returns `false`. The note is required and retained in `close_write_off_note`. `tempo_session_close_report_written_off` carries the channel and `amount_forgone_native`, the builder payout being abandoned in native token units. This discharges that report's cleanup blocker; it does not discharge caller refund liabilities, move money, or declare a refund paid. Use it only after deciding to abandon the missing builder report. If that written-off close lands later, its payout is not reported: the recorded write-off forgoes it. `retryHostedTempoCloseReport` can reopen the written-off `no_report` row before that close lands; restore complete history and reopen it before the late landing if the payout should still be reported.

The session sweep and hosting closure reconciliation also finish `exit_required` drains without another caller poll. A cooperative close requires its receipt's refund amount. A payer exit requires a finalized empty channel, matching payer-exit history, and retained pre-finalization collateral; the collateral less settled vouchers is a lower bound on the payer refund. The bound must cover the exact drain debit. The drain becomes `sent` together with its durable drain report, and its settlement evidence records `terminal_outcome: "payer_exit"` or `"cooperative_close"`. If its last voucher was unpaid, the credit stays `unbacked`, the outcome gains `_unbacked`, and `tempo_session_drain_unbacked_resolved` carries the caller amount, proven refund, and builder voucher loss. This records a refunded caller separately from an unpaid builder voucher. Otherwise, completion emits `tempo_session_drain_finalized`. A completed drain remains readable even when its credit is unbacked.

Missing close history, unavailable collateral, and a short refund leave the drain open and emit `tempo_session_drain_refund_unproven` with the channel, caller amount at stake, and reason. Each distinct reason emits once per drain; warning claims are retained in the channel snapshot across restarts and shared-store replicas. Transient RPC failures and failed accounting/report writes leave it open and emit `tempo_session_close_reconcile_failed` instead; they do not declare a refund unproven. Older finalized rows without a retained collateral snapshot need independent receipt evidence; empty state alone cannot discharge them. The sweep never restores or debits the credit again.

Both SDK ledgers implement `requireTempoDrainExit`. A custom ledger without it receives the explicit timed-exit HTTP 409 with `status: "pending"` instead of a server error, but cannot persist the refusal or participate in automatic terminal drain recovery. Its response permits a retry with a corrected credential when cooperative attempts remain; that retry can broadcast, and keeps the original debit. Implement that capability for the same durable behavior; the fallback keeps the original debit and never broadcasts another close after hosted exhaustion.

The same retry can repair an incorrectly inferred payer exit. `tempo_session_close_exit_resolved` is inferred from the latest uncancelled payer close request after its grace period, because withdrawal has no separate event. An RPC node that omits a cooperative close during that period can cause a false `no_report` result. Restore complete logs before reopening the report. Upgrading adds `exhausted` and `unmatched` to the report-state constraint and the nullable `close_write_off_note` column without changing existing rows. Initialization compares the constraint definition and only replaces it when necessary; later boots retain the same constraint without another validation scan. The session snapshot retains `depositBeforeFinalization` when it observes finalization; `exit_required` is an additional drain status. Upgrade every instance sharing these stores before serving terminal drains with the new status.
